# Run locally and deploy later

No paid hosting is available. No hosted service has been provisioned or deployed, and no Railway/Render target is configured. This step supplies runnable artifacts and optional host-neutral CI wiring, not a fictitious public deployment. Docker is available locally; see VERIFICATION.md for the actual build, test and Compose results.

## Local run

Prerequisites: the SDK pinned in global.json, Python for the one-time secret generator, and Docker with Linux containers/Compose. From the repository root:

1. Run `python scripts/create-local-env.py` once. This creates ignored local credentials without printing them; it refuses to overwrite an existing .env.
2. Run **`docker compose up --build --wait`**. This one command starts PostgreSQL, completes the two explicit migration tasks, then starts API and gateway. Normal service startup does not migrate. No database port is exposed to the host.
3. Check `http://localhost:8080/health/live` and `/health/ready` for API; use port 8081 for gateway. Both readiness probes should return 200. Responses contain only health status; JSON request logs include generated X-Correlation-ID, status and duration, without submitted headers/query strings/IPs.
4. Run `dotnet build Labaik.sln --configuration Release` and `dotnet test Labaik.sln --configuration Release`. Testcontainers starts its own isolated PostgreSQL; it does not depend on the Compose DB. Do not treat a Docker failure as a passing or skipped integration test. Domain.Tests covers the state/role matrix and integer pricing/voucher rules.
5. Stop local services with `docker compose down`; the database volume is retained. Do not regenerate passwords against a retained volume; database role rotation is a separate operation.

For host-process runs, set ConnectionStrings__Database explicitly (dotnet run does not read .env) and optionally ASPNETCORE_URLS. Use a runtime role, not a migrator role. API exposes authenticated booking, offer, file, payout and operations endpoints plus signed gateway callbacks. Gateway simulation and transaction reporting require its private API key. Never expose that key to customer browsers.

## Numbered managed-host deployment steps (manual, later)

1. **Review verification:** require the full database/load suites to pass and build/run both images. Review artifacts/tests and the vulnerability report. No external deployment is needed to finish this verification.
2. **Connect GitHub:** create your repository/remote and push this commit to dev-main; create main for production. CI also supports manual dispatch. Permit Actions to publish repository GHCR packages. It publishes separate API/gateway images tagged with the immutable commit SHA; a pull request only verifies. No remote/push or registry publication was performed locally.
3. **Choose an available host:** select a managed container host and PostgreSQL service supporting the pinned .NET runtime images, private networking, schema-owner/runtime credentials and one-shot migration tasks. No provider was selected here and no paid resource should be created as part of this skeleton. Configure separate staging/production resources when available.
4. **Bootstrap the existing database once:** supply administrator psql connection/TLS variables and the five role-password variables through the host's secret manager (names in ENVIRONMENT.md), then run deploy/postgres/001-schemas.sh against that existing database. Review it with the host's permissions first; it creates fixed runtime/migrator roles and app/fake_gateway schemas, restricts public schema creation, and gives each runtime only its own schema. On managed hosts the administrator need not be named postgres. Never grant runtime schema creation or inject the administrator credential into the applications.
5. **Configure runtime services:** select the two GHCR images from the same tested SHA. Set each service's ConnectionStrings__Database to its own runtime login, configure finite database timeouts and validated TLS, set production hosting and the container listen port. Provide private DB reachability and registry pull credentials if packages are private; terminate HTTPS at the host's ingress.
6. **Run migrations before rollout:** launch a one-shot task from the API image with argument `--migrate`, using only the app migrator connection string; repeat with gateway image and gateway migrator string. The images already have their dotnet entrypoints, so override arguments, not the executable. Require zero exit status from both. Each service has its own schema-local EF history table; all current migrations must apply, including business entities. A nonzero result stops rollout; no HTTP startup auto-migration exists in any environment.
7. **Roll out the HTTP processes:** run each image with its default arguments and runtime credentials only. Configure `/health/live` for process liveness and `/health/ready` for ingress readiness. Readiness checks live PostgreSQL and schema USAGE. Core additionally checks its own worker heartbeat when workers are enabled, and private blob availability when storage is configured. Missing optional storage configuration leaves file operations unavailable; a healthy minimal stack does not prove file readiness. Route traffic only after readiness succeeds.
8. **Verify staging before production:** GET both health paths through HTTPS, inspect correlation/structured logs, confirm unknown paths return 404, and verify unauthorized mutations fail. Exercise DB-unreachable readiness only in staging or the automated container test; liveness stays 200 while readiness becomes 503. Record the real public URLs and verification evidence in DESIGN.md when a deployment actually exists.
9. **Optionally wire deployment jobs:** configure staging/production GitHub environments. With no HOST_DEPLOY_URL/TOKEN, jobs log a clear skip and remain successful. Only set them after implementing a host-side HTTPS orchestrator accepting `{revision, images: {api, fake-gateway}}` with bearer auth. Its synchronous HTTP 200 contract must mean migrations completed successfully, both exact-image rollouts and readiness checks finished; an asynchronous 202 is not success. scripts/deploy-managed.py is only a client for that contract, not an implemented provider adapter. Protect production with environment approval if desired.
10. **Keep migrations safe:** future changes expand first, deploy compatible application versions, then contract in a later release. Keep backups and roll back the application image where compatible; never automatically downgrade database schema during rollback or let replicas race startup migrations. Document provider-specific commands after selecting a host.

## Identity setup and explicit staff provisioning

1. Apply the Identity migration with the existing explicit API --migrate task before enabling auth traffic. Runtime startup still never migrates.
2. Configure Firebase project/service-account JSON and independent JWT/recovery keys from ENVIRONMENT.md on the API. New .env generation includes auth keys; for an existing step-1 .env, preserve database passwords and add only missing auth keys/project/credentials. Without these settings health remains available; auth returns unavailable/unauthorized, never a fabricated identity.
3. A client sends its Firebase ID token to POST /auth/firebase; send the returned access token as a Bearer token to GET /auth/me. Refresh uses POST /auth/refresh with the opaque refreshToken and a freshly generated random UUID-N requestKey per rotation. Retry a lost response with the exact same parent/key within 15 seconds; persist the returned tokens atomically on the client. No cookies or email-based account selectors are used. HTTPS is required outside local development.
4. Provision a staff/performer identity only through the API image's --provision-user operator command, with Provisioning__FirebaseIdToken and Provisioning__Role injected as temporary secrets plus normal auth/DB configuration. The real verifier checks that exact token/UID first, then a transaction grants the explicit role and revokes existing refresh families. The operator's access to this command/credentials is the administrative trust boundary; there is no public provisioning/role-grant endpoint. Remove provisioning secrets after execution. Existing access JWTs can retain old privileges until their 10-minute expiry.
5. IP limits use the actual socket remote address; untrusted X-Forwarded-For is ignored. Behind an ingress this conservatively shares the ingress IP's budget. Configure a known-proxy/known-network forwarding policy for your specific host before relying on original client-IP separation; do not blindly trust arbitrary forwarded headers. Account budgets still work across all replicas/IPs and invalid claimed emails never select an account bucket.
6. Maintain synchronized clocks, outbound access to Firebase certificate/OAuth/revocation APIs and shared DB reachability. Authentication infrastructure failures return unavailable and never issue tokens. Cleanup clears expired recovery ciphertext on a five-second timer (up to about five seconds of physical retention beyond the 15-second usable window); hashes remain for replay detection. Limiter buckets older than ten minutes are deleted idempotently. No advisory lock is needed for these idempotent cleanup statements.

The real adapter follows [Firebase ID token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens) and enables the additional [revocation check](https://firebase.google.com/docs/auth/admin/manage-sessions). Tests replace HTTP with local test certificates/OAuth/user responses to run the actual SDK logic without a live project; successful live Firebase exchange still requires your configured project credentials.

## Current business-service activation

1. Preserve the existing ignored .env. Run `python scripts/add-payment-env.py` to append missing payment keys without rotating PostgreSQL/auth secrets.
2. Compose enables the Core durable worker and fake gateway callback dispatcher. The API now has booking/cancel/checkout/return, offer acceptance/suspension, private files, completion/dispute, payout CSV/result and accountant operations routes. Firebase credentials are required for actual client login; there is no public seed or role-grant endpoint.
3. Configure a private Azure Blob account/container with Storage__ConnectionString and Storage__Container for file operations. Use HTTPS in a managed environment. Client upload must use one Put Blob request with x-ms-blob-type BlockBlob; create-only SAS intentionally disallows overwrites/block staging. Set MIME metadata correctly; complete upload, supervisor approve, then complete booking. Grant the container only to the application's credential. Storage is optional for the health-only local stack; file operations fail closed without it.
4. Configure Payouts__PerformerFeeMinor and Payouts__Accounts__<performer UUID> through trusted secret configuration. Accounts must pass Saudi IBAN syntax/checksum validation. Batches use closed UTC weeks; the weekly worker claims available earnings and an accountant exports CSV, sends it through the bank separately, then records a confirmed Paid or Failed result and unique bank reference. Unknown outcomes remain Pending. Never re-submit an exported file until the bank outcome is resolved. Bank-specific CSV acceptance is not certified here.
5. For email, configure Notifications__EmailApiKey, Notifications__EmailFrom and Notifications__EmailRecipients__<user UUID>. Recipients are operator-maintained verified destinations, not identity selectors. No configured address means no email delivery is requested. Users register FCM registration tokens and locale through authenticated POST /notifications/device. Real FCM/email delivery needs provider credentials and a reachable recipient/device; local tests use a controlled transport. Email provider is Resend; FCM uses Firebase Admin SDK. Registration-token support is retained explicitly while the SDK moves toward FIDs.
6. The nightly job compares paged gateway captures/refunds with local ledgers and stores a bounded mismatch report on JobRun. GET /operations is active-accountant/admin only and shows reports, persistent payment alerts and dead letters. Reports observe a moving system: inspect recent mismatches after workers drain before taking manual action. They never invent money or bypass gateway verification. At most 25,000 remote captures are scanned; larger runs fail visibly for operator follow-up.
7. An instance writes its own worker heartbeat every five seconds; readiness fails if it becomes older than thirty seconds. Jobs use persisted leases/fencing and resume after restart. Failed jobs retry with backoff then dead-letter. Investigate outcome before resetting a dead letter: keep the same job/entity/provider keys, never create a replacement charge or unknown bank transfer. No public retry-everything button is provided.
8. Optionally set OTEL_EXPORTER_OTLP_ENDPOINT (and protocol/headers where required) to your collector. Basic explicit HTTP/worker spans export method/status/job kind; arbitrary URLs, queries, token headers, bodies and personal identifiers are excluded. No collector/dashboard or real provider deployment has been verified locally.
